# 《AI 互动学习闯关小程序》方案设计文档（确认稿）

## 一、文档概述

### 1.1 项目目标

本项目面向中小学生学习场景，目标是将用户输入的学习内容自动转化为“可答题、可讲解、可复盘”的互动学习体验。  
首版不追求做成完整教育平台，而是优先验证最核心的业务闭环是否成立：

`用户输入内容 -> AI 解析知识 -> AI 生成题目 -> 用户答题 -> AI 生成学习报告`

### 1.2 首版设计原则

- 先跑通核心业务，不优先做账号、数据库、分享、排行榜等外围系统
- 先做最容易稳定落地的输入形式，不一开始扩展 PDF、网页、视频链接
- AI 输出必须结构化、可校验、可回溯，不能直接把模型自然语言当结果用
- 所有方案优先服务于“独立开发者可快速搭建、快速联调、快速验证”

### 1.3 首版范围结论

首版 MVP V1 只覆盖以下范围：

- 输入方式：`文本粘贴`
- 题型范围：`单选题`、`判断题`
- 学习流程：`单次匿名学习会话`
- 报告范围：`本次会话报告`
- 不包含：`登录注册`、`学习历史`、`云数据库`、`排行榜`、`分享裂变`、`家长端`

## 二、技术选型与对比

### 2.1 小程序前端技术选型对比

本项目重点比较 3 条路线：

#### 方案 A：微信原生小程序

**优点**

- 与微信生态贴合最紧密
- 原生 API 使用最直接
- 兼容性和平台能力最完整
- 对文件、分享、开放能力接入最少绕路

**缺点**

- 工程化能力一般
- 组件复用、状态管理、复杂页面组织成本更高
- 代码规模一旦扩大，维护成本上升明显
- 对独立开发者来说，长期迭代效率不占优

**适用场景**

- 强依赖微信开放能力
- 页面结构简单
- 团队长期只做微信小程序单端

#### 方案 B：uni-app（Vue3）

**优点**

- 上手快，开发效率高
- 多端输出能力成熟
- Vue 生态对很多开发者友好

**缺点**

- 多端抽象越多，平台差异处理越绕
- 在复杂状态流和中等规模项目中，工程组织不一定比 React 更清晰
- 首版虽然只发微信端，但如果为了“也许以后多端”而过早引入额外抽象，收益有限

**适用场景**

- 已有 Vue 技术积累
- 未来明确要快速扩到多个客户端
- 页面逻辑偏表单和内容展示

#### 方案 C：Taro 4 + React + TypeScript

**优点**

- 工程化能力强，适合模块化演进
- React 组件化和状态流更适合承载后续答题流程、生成状态、报告展示
- TypeScript 对接口契约和 AI 结构化数据联调更友好
- 后续扩展到 H5 或其他端有更好延展性
- 对独立开发者而言，前端结构可控性更高

**缺点**

- 个别微信原生能力仍需直接处理平台差异
- 首次搭建比原生方案略重
- 如果最终永远只做非常轻的小程序，原生方案在简单度上更直接

### 2.2 小程序前端最终结论

首版推荐路线：`Taro 4 + React + TypeScript`

**原因**

- 能兼顾 MVP 迭代效率与中期扩展性
- 更适合把“输入、生成中、答题、报告”拆成清晰状态流
- 更适合后续沉淀组件和页面逻辑
- 方案稳定，不会因首版过度追求新能力而增加不必要风险

### 2.3 Skyline 策略

- `Skyline` 定位为后续性能优化选项，不作为首版基础依赖
- 首版不围绕复杂动画、worklet、重交互特效做设计
- UI 以稳定、流畅、低复杂度为主，优先保证完整闭环和联调效率

### 2.4 后端与 AI 技术选型

#### 后端语言与框架

推荐：`Python + FastAPI + Pydantic + Uvicorn`

**原因**

- Python 生态更适合 AI 编排与文本处理
- FastAPI 天然适合快速搭建接口、定义请求响应模型
- Pydantic 适合做结构化输出校验
- 对独立开发者而言，开发速度和可维护性都较优

#### AI 编排框架

推荐：`LangChain`

**定位说明**

LangChain 在本项目中不是“为了炫技而加的抽象层”，而是承担以下职责：

- 管理多段 Prompt 模板
- 串联知识提取、出题、讲解、报告四段链路
- 对接 DeepSeek 模型调用
- 组织结构化输出与失败重试
- 为后续替换模型供应商保留统一适配层

#### 模型供应商

首版默认：`DeepSeek`

**原因**

- 国内接入和调试更友好
- 成本相对可控
- 足够支撑文本总结、出题、讲解、报告等首版需求

## 四、核心业务流程设计

### 4.1 用户主流程

1. 用户进入输入页
2. 粘贴学习文本
3. 选择题目数量
4. 提交生成请求
5. 后端进行知识提取与出题
6. 前端进入生成中页展示进度状态

8. 用户逐题作答
9. 每题作答后获得即时反馈和讲解
10. 所有题目完成后请求学习报告
11. 展示报告页

1. 接收原始文本
2. 文本清洗与长度校验
3. 知识点提取
4. 题目生成
5. 题目结构校验
6. 用户答题后返回即时判定
7. 汇总答题结果
8. 生成学习报告

功能：

- 返回重新输入入口

#### 3）答题页

功能：

#### 4）报告页

## 五、系统架构设计

### 5.1 总体架构

系统采用“微信小程序前端 + Python AI 服务端”的双层结构：

- 小程序前端负责交互和展示
- Python 服务端负责 AI 能力编排和结构化输出
- 首版不引入独立数据库服务
- 会话数据采用内存会话管理，必要时本地文件兜底

### 5.2 前端职责

前端只承担以下职责：

- 收集用户输入
- 调用后端接口
- 管理页面状态
- 组织答题流程
- 展示题目、反馈和报告

前端不承担：

- 知识抽取逻辑
- 题目生成逻辑
- 报告生成逻辑
- AI Prompt 编排

### 5.3 后端职责

后端承担以下职责：

- 输入文本校验与清洗
- AI Prompt 编排
- 知识提取
- 题目生成
- 题目结构校验
- 提交答案后的判定与讲解返回
- 会话状态管理
- 报告生成
- 错误处理与重试

### 5.4 模块划分建议

## 六、AI 设计与 LangChain 编排方案

### 6.1 为什么必须正式采用 LangChain

输出计划中的 todo 已经可以确认，应转化为正式决策：

> AI 大模型对接采用 Python 的 LangChain 作为编排框架

这不是附属技术点，而是后端设计核心之一。

### 6.2 LangChain 在本项目中的职责

- 定义知识提取 Prompt
- 定义题目生成 Prompt
- 定义讲解生成 Prompt
- 定义报告生成 Prompt
- 封装模型调用参数
- 处理结构化输出
- 统一错误处理与重试
- 保留未来模型切换适配层

### 6.3 AI 生成链路拆分

#### 链路 1：知识提取链

输入：`sourceText`  
输出：

- `knowledgePoints[]`
- `summary`
- `difficultyHints`

#### 链路 2：题目生成链

输入：

- `sourceText`
- `knowledgePoints[]`
- `questionCount`

输出：

- `questions[]`

每道题包括：

- `id`
- `type`
- `stem`
- `options`
- `correctAnswer`
- `explanation`
- `sourceEvidence`

#### 链路 3：即时讲解链

首版建议默认在出题阶段一并生成 `explanation`，答题时直接返回。  
这样可避免每答一题再次请求模型，降低时延与成本。

#### 链路 4：报告生成链

输入：

- `sourceText`
- `knowledgePoints[]`
- `questions[]`
- `answerRecords[]`

输出：

- `accuracy`
- `wrongQuestions`
- `weakPoints`
- `summary`

### 6.4 AI 输出约束

所有模型输出都必须满足：

- 输出为固定 JSON 结构
- 后端使用 Pydantic 校验
- 校验失败可自动重试有限次数
- 连续失败后返回可理解错误提示
- 每题必须包含 `sourceEvidence`

### 6.5 幻觉控制策略

- 题目必须基于用户输入内容生成
- 不允许生成无法从原文支撑的知识点
- 每题附带原文依据片段
- 报告只描述本次答题表现，不做过度教育判断
- 对输入质量较差内容，直接提示“内容不适合出题”

## 七、接口设计

### 7.1 创建学习会话

`POST /sessions`

**请求参数**

- `sourceText: string`
- `questionCount: number`

**响应参数**

- `sessionId: string`
- `status: "processing" | "ready" | "failed"`

### 7.2 获取会话状态与题目

`GET /sessions/{sessionId}`

**响应内容**

- `sessionId`
- `status`
- `knowledgePoints[]`
- `questions[]`
- `errorMessage`

### 7.3 提交题目答案

`POST /sessions/{sessionId}/answers`

**请求参数**

- `questionId: string`
- `selectedAnswer: string`

**响应参数**

- `isCorrect: boolean`
- `correctAnswer: string`
- `explanation: string`
- `sourceEvidence: string`

### 7.4 获取学习报告

`GET /sessions/{sessionId}/report`

**响应参数**

- `accuracy: number`
- `wrongQuestions[]`
- `weakPoints[]`
- `summary: string`
- `durationSeconds: number`

### 7.5 接口设计原则

- 首版保持接口数量少，便于联调
- 所有状态围绕单次 session 组织
- 不提前为“用户体系”设计复杂鉴权模型
- 错误码与错误信息应明确区分：
  - 输入错误
  - AI 输出错误
  - 会话不存在
  - 会话未完成

## 九、开发流程与实施思路

### 9.1 实施原则

- 先后端，后前端
- 先打通接口，后补页面体验
- 先单次会话，后考虑历史记录
- 先稳定结构化输出，后讨论复杂玩法

### 9.2 分阶段开发流程

#### Phase 0：后端 AI 最小链路验证

目标：

- 输入一段文本
- 返回结构合法的题目列表

完成内容：

- DeepSeek 接入
- LangChain Prompt 拆分
- Pydantic 输出校验
- `/sessions` 和 `/sessions/{id}` 基础能力

#### Phase 1：前端最小闭环接入

目标：

- 跑通输入 -> 生成 -> 答题

完成内容：

- 输入页
- 生成中页
- 答题页
- 提交答案接口联调

#### Phase 2：报告与异常处理

目标：

- 跑通完整业务闭环

完成内容：

- 报告生成
- 报告页
- 错误提示
- 重试机制
- 会话状态完整流转

#### Phase 3：首版稳态优化

目标：

- 提升可测试性和可用性

完成内容：

- 输入长度限制

- 耗时与错误日志
- 成本控制开关
- 基础埋点

### 9.3 明确暂缓事项

以下内容不能插队进入首版：

## 十、风险与控制策略

### 10.1 AI 幻觉风险

**风险**

- 题目答案错误
- 解析与原文不一致
- 报告误判知识薄弱点

**控制**

- 强制 `sourceEvidence`
- 结构化校验
- Prompt 明确禁止脱离原文扩写
- 必要时加入二次校验链

### 10.2 输入质量风险

**风险**

- 文本太短
- 文本噪声太多
- 不具备可出题性

**控制**

- 输入字数上下限
- 内容预清洗
- 返回“内容不足以生成高质量题目”的提示
- 不强行对垃圾内容出题

### 10.3 成本风险

**风险**

- 长文本导致 token 成本过高
- 单次题量过多导致调用成本失控

**控制**

- 限制文本长度
- 限制题目数量
- 出题和报告生成分层控制
- 即时讲解尽量随题预生成，避免逐题二次调用

### 10.4 未成年人产品风险

**风险**

- 内容安全
- 隐私风险
- 学习评价表述不当

**控制**

- 对输入做基础内容安全检查
- 不要求首版采集个人身份信息
- 报告文案保持中性
- 不做诱导分享和沉迷机制

## 十一、测试与验收标准

### 11.1 功能验收

- 用户能提交有效文本
- 后端能返回 5 到 10 道结构合法题目
- 用户可逐题完成答题
- 每题都能返回正确答案与讲解
- 用户可在完成后看到完整报告

### 11.2 数据与结构验收

- 单选题答案唯一
- 判断题答案值域固定
- 所有题目字段完整
- 接口返回结构固定
- 会话状态流转正确

### 11.3 质量验收

- 至少 80% 题目带 `sourceEvidence`
- AI 返回异常 JSON 时，服务端能处理
- 空输入、短输入、异常输入时有明确提示
- 连续多次生成不会串会话数据

### 11.4 性能体验验收

- 生成流程可感知，不让用户停留在无反馈状态
- 答题交互流畅
- 报告页加载可接受
- 前端页面不因异常数据直接崩溃

## 十二、结论

本项目首版的正确打开方式不是“先把平台搭完整”，而是把最短业务闭环做透。  
因此，首版《方案设计文档》的最终结论应明确为：

- 前端采用 `Taro 4 + React + TypeScript`
- 后端采用 `FastAPI + Pydantic + Uvicorn`
- AI 编排采用 `LangChain`
- 模型供应商首选 `DeepSeek`
- 首版输入只做 `文本粘贴`
- 首版只支持 `单选题 + 判断题`
- 首版只做 `单次匿名学习会话`
